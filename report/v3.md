## Policy chosen on train
- Escalate when: the PR type is launcher or workflow (always the maintainer), the model asks for the maintainer, confidence < **0.65**, the PR edits a TV list already on main, the critic finds a rule-backed blocker to a merge, or the cheap second opinion disagrees on the class. Deterministic overrides (binaries, sensitive paths, protected packages, INTERNET, strings missing in most locales, an existing list folder) always win.
- On train (dev2) this gave precision 1.0 at coverage 0.337 with 0 wrong merges.

## Rules learned from your past decisions
Applied to MAINTAINER.md (please confirm):
- ✅ A PR that bundles several good, separable parts gets rework with one ask: split it into separate PRs, listing each part and what it needs. Close a bundle only when its idea has already landed another way or it has fallen far behind main. A PR that adds one device's list plus small fixes or options for that same device can be merged as one PR. (from #326, #268, #83, #67)
- ✅ Close, rather than hold, contributor PRs whose main content is a new CI workflow that builds or publishes releases (for example a 'latest' APK on every push), especially when they have no description or are bundled with other changes. Hold is for workflow changes that are clearly argued and could plausibly be adopted. (from #112, #416)
- ✅ Launcher bug fixes that correct wrong behaviour (focus or highlight glitches, wrong tuner or activity being opened) don't need a config flag and don't need a hold for a fresh TV run when the author tested the fix on a device. The TV-run hold is for new visible features. A good feature with small performance issues can be merge-with-fix, with the maintainer making the fix. (from #339, #436, #356)
- ✅ Close kindly anything that goes against the project's base rule ('no root, nothing uninstalled, you build it yourself'), even if it is only docs or a showcase row. That includes root exploits, getting around app-store protection, prebuilt APKs, private or modified builds others can't reproduce from this repo, and extras added to the PROMPT flow beyond debloating (such as system-wide DNS or ad blocking). If there is a public, reproducible version, point to it. (from #347, #396, #136)
- ✅ Before accepting that a feature is 'off by default', check the diff, not the description. The flag must exist in config.xml, the theme JSON and the themes/README table. When the flag is off, nothing new should run: no receivers registered, no writes, no permission grants in the install script. If any of that runs while the flag is off, the verdict is rework. (from #311, #257)
- ✅ When two open PRs build the same helper or fix, choose one as its home and ask for rework on it: the other author folds their part in. A draft that overlaps another PR gets this rework ask, not a hold. If another PR already fixes the same thing more completely, close the narrower one. (from #402, #425)
- ✅ If a launcher change is a different design or taste for everyone (for example, its own sounds replacing the system click) and the author is still deciding on an opt-in version, hold it and add the author's branch to SHOWCASE.md in the meantime. Don't send it back for rework. (from #28)

Not applied (your call; they loosen a safety rule or contradict your recent rounds):
- ⏸ Missing translations alone are not a rework. If an opt-in launcher feature is otherwise good and only some locales lack the new strings, use merge (or merge-with-fix: 'add the strings to the other locales on merge'). The maintainer fills them in. Send it back for rework only when the behaviour itself needs changing. (from #115, #264, #385)
- ⏸ If a small, tested fix to the Home-guard or disable scripts only makes the guard stricter or more accurate (for example, not counting a vendor FallbackHome as a second launcher), it can be merged or merged-with-fix. Hold only changes that loosen the guard or redesign the flow. If main has already solved the same problem another way, close kindly and point at what landed. (from #435, #58)
- ⏸ A different model number gets its own examples folder even if it shares a board, chip or firmware with a list already on main. That is not a duplicate. Treat it as a duplicate only when it is the same model or the same folder. Fix small metadata mistakes (chip name, device name) on merge. (from #205, #295)
