## What the policy does (`maintainer_bot/v4.py`, no model calls)

1. **Always the maintainer**, whatever the verdict: PROMPT.md, `tools/disable*`, `tools/restore*`, `.github/`
   (workflows, the bot's rules), lists that disable protected packages. No model call is made for these.
2. **A merge is stopped** (hold) by: pairing/input packages, `pm hide` without an undo, maintainer-only paths,
   prebuilt binaries, a new permission or network use in the launcher, more than 220 lines of launcher code
   (tests and translations don't count).
3. **A merge becomes a rework** for: an APK over the gate (when known), red CI (when known), a changed default
   for every TV, new strings missing in more than two locales, a code conflict with main (a table-row conflict
   doesn't count), `pm uninstall` steps.
4. **A rework the model asks for on a launcher change over 100 lines goes to the maintainer** (rework, or a home
   in the showcase/addons? chosen after the test, see the rules below).
5. **Judgement calls need more confidence:** a launcher merge 0.75; Home/launch path, manifest or an edit to a
   list on main 0.85; a new folder for a product already on main 0.75 for *any* verdict (fold in vs own folder).
   Everything else 0.65.
6. **Then** the critic (every code merge and every judgement-call merge) and the second opinion (it must point
   the same way: showcase, addon and close all count as "not here").
7. **Fixes added on merge:** strings missing in one or two locales, the Private DNS setup, the folder's own
   scripts, untested entries, files nothing links to, a missing theme screenshot.

## Re-review (why #670 and #730 went stale, and the fix)

The live workflow put every event for a PR in one concurrency group with `cancel-in-progress`. Both authors
pushed and, a second later, commented "Done: …" (#730 at 17:41:55/56Z, #670 at 21:30:23/24Z). The comment
started a run in the same group, which cancelled the push's review; the comment run itself was then skipped
by the job's `if`. Since go-live, 12 of the 17 push reviews that were cancelled were cancelled this way.

- Comments that don't start with `/bot review` now get their own group (keyed by run id), so they can't cancel.
- Every push is reviewed again. If the PR's own changes (paths and +/- lines) are the same as at the last review
  (a rebase, main merged in), or only Markdown changed on a code or list PR, the bot keeps its stored judgement
  and only re-runs the facts and the policy: no model call, about 15 s of runner time. Docs and showcase PRs,
  whose Markdown *is* the change, always get a full review.
- A 6-hourly `schedule` sweep reviews any open PR whose sticky is older than its head (and, once, every v1
  review, so the queue only holds v4 reviews: about 50 PRs, ~$2.50).
- `/bot review` stays limited to OWNER/MEMBER/COLLABORATOR; authors don't need it any more.

## APK size (designed, off by default)

The launcher gate is the one fact the diff can't give: #525 (+1.2 KB) and #724 (+1.9 KB) were closed as "bigger
than the budget" although their code looked small. The bot must never build PR code itself
(`pull_request_target` runs with secrets), but CI already builds the release APK on every PR. So:

1. CI (`ci.yml`, launcher job, after "The launcher stays small"):
   ```yaml
         - run: echo "$(stat -c %s launcher/app/build/outputs/apk/release/app-release.apk) gate 471040" > apk-size.txt
         - uses: actions/upload-artifact@<pinned sha> # v4
           with: { name: apk-size, path: apk-size.txt, retention-days: 3 }
   ```
2. maintainer-bot workflow: `apk-size-artifact: apk-size`, `actions: read`, and a second trigger
   `workflow_run: { workflows: [CI], types: [completed] }` running the action with `mode: refresh`. A refresh
   re-runs only the facts and the policy on the stored judgement (no model call), so a red CI or an APK over the
   gate turns a suggested merge into a rework within a minute of CI finishing. Fork PRs are found by head owner
   and branch, since `workflow_run` carries no PR list for forks.
3. **Cost:** no extra build and no model call. About 5 s per CI run for the upload, a 20-byte artifact kept 3 days,
   and one ~20 s bot run per finished CI run. At go-live day's rate (~180 pushes in 10 hours) that is roughly
   2 runner-hours a day, free on a public repo. Building the APK in the bot's own job instead would cost 4–6
   minutes per push (10+ runner-hours a day at that rate) and duplicate CI, so it is not offered.

## How to switch it on, in detail
1. Push the bot: `cd ~/Arsenal/maintainer-bot && git push origin v4` (this also publishes the phase-2 commits
   already on local master; phase 2 stays off). The cleanyourtv branch already pins the workflow to v4's head
   (`git -C ~/Arsenal/maintainer-bot rev-parse v4`), so push exactly that commit.
2. Create the three labels:
   `for l in bot-suggests:showcase bot-suggests:addon bot-suggests:theme; do gh label create "$l" -R Gathin23/cleanyourtv --force; done`
3. cleanyourtv: push the local branch and merge its PR (it touches `.github/`, so the bot skips it):
   `git -C ~/Arsenal/tv-vibehack push origin bot-v4-context && gh pr create -R Gathin23/cleanyourtv --head bot-v4-context --fill`
   It updates `.github/maintainer/MAINTAINER.md` (v4 policy), `precedents.jsonl` (676 decisions) and the
   workflow (pinned to v4, the comment-cancel fix, the 6-hourly sweep). The bot reads rules from main, so v4
   starts with the merge.
4. The first sweep (within 6 hours, or `gh workflow run maintainer-bot.yml -R Gathin23/cleanyourtv`) re-reviews
   the ~50 open PRs once with v4: about $2.50.
5. Optional, later: the APK-size fact (below). Rollback: re-pin the workflow to `b303f262…`.
